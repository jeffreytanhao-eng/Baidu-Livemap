# 百度地图15分钟生活圈（Livemap）

**指定社区中心，在「不能穿墙、不能淌水、不能上封闭汽车道」的约束下，画出沿真实路网步行的 X 分钟生活圈（缺省 15），并给出 7 类民生设施体检报告。**

产品围绕两个场景：**在特定地点附近找小区**（附近小区生活圈），以及**给特定小区出生活圈评价**（评估小区生活圈）。

2026 上海开源软件应用创新大赛 · 开源 AI 工具赛道 · 百度地图企业命题参赛作品。

版本支持**北京六环内区域高精度结果**；六环外区域自动降级为走廊近似（见「系统技术架构」）。

## 一、使用方法

### 1.1 引导页面与两个场景

打开 http://localhost:3000 首先是**场景选择页**，两个入口：

**场景 A · 附近小区生活圈（`/nearby`）**——「我想在这个位置附近找小区」

1. 地图空白处**单击即选点**（POI 层默认关闭，避免设施点拦截选点），400 ms 防抖后查询；
2. 右侧列出周边 **1 km 内小区**：名称 + 直线距离，按距离升序；
3. 每条小区可「**在地图定位**」（地图平移至该小区并挂高亮标记）或「**取消定位**」；
4. 一键跳转场景 B（URL 带小区坐标），自动开始评估；从评估页回退时用 sessionStorage 保留列表与滚动位置。

**场景 B · 评估小区生活圈（`/evaluate`）**——「给这个小区的生活圈打分」

1. 地图上选点即评估中心；点落在住宅小区（residential 面）内时自动匹配内置小区库，命中后在定位点右侧弹出**小区资讯框**：照片、售卖均价、一居/两居/三居租金区间、简介（右上角可关闭）；
2. 支持 URL 参数 `?lat=&lng=&minutes=` 回填；样例中心（劲松/中关村/南苑/上地 150 m 内）+ 默认 15 分钟**自动跑一次**，URL 指定坐标（如附近页跳转）也自动跑；
3. 其余操作见 1.2。

### 1.2 评估场景操作流程

1. **调参数（不发请求）**：顶栏分段控件 `5 / 15`（15 带 `*` 是默认）；地图上单击选点或拖动红色中心标记（松手生效）。改完出现「参数已改，尚未体验」，报告区盖「以下为上次 X 分钟结果」水印——看到的仍是旧结果。
2. **点「开始体验」（唯一计算入口）**：两拍出圈——快拍「正在快速出圈…」约 300 ms 铺出沿路等时斑；精拍「正在叠加建筑与设施检索…」出建筑让位后的分层多边形、覆盖打分与体检报告。同一中心 + 同一分钟再点命中缓存，毫秒级返回。
3. **读报告（右侧栏 5 张卡 + 操作行）**：
   1. **综合得分**：0–100 居中展示；演示/降级时附对应徽标；
   2. **七类设施达标雷达**：连续近度分（越近分越高），60 分线即达标线，形状与下方条形图逐条对应；
   3. **最近设施步行分钟**：横条图，红色虚线 = X 分钟阈值；
   4. **达标明细**：类别 / 数量 / 最近步行分钟 / 是否达标；**行悬停弹出设施浮层**（设施名 + 步行距离 + 步行分钟，重点设施带徽标），点设施名即在地图上定位高亮；
   5. **体检诊断**：3–6 条白话结论，带方位徽标指认缺口方向。

   末尾操作行：打印 / 下载 JSON / 复制分享链接（链接带 `lat,lng,minutes`，打开即回填）。
4. **图层（左下「图层」面板）**：等时分层、路网、建筑可进入性、水域、快速路/阻隔、设施点、服务盲区(1km) 七项默认全开，开关即时生效；面板附等时图例（5 分钟绿 / 10 分钟蓝 / 15 分钟琥珀）、建筑四色、7 类设施色例与盲区纹理图例（红框 + 斜线↗/斜线↘/圆点 = 1 km 内缺菜市场/超市、药店/医院、小学，见「设计思想 6」）。**建筑四色**：青 = 可进入（商场）、深青描边 = 裙楼底商、灰 = 封闭院落（住宅，不可穿）、浅绿 = 开放空间。

### 1.3 口径与规则

- 等时分层随 X 变化：15 → 5/10/15 三层；其它取值 2–4 层且必含 X；覆盖达标阈值 = X 分钟，直线对照圆半径 = 80 m/min × X；
- 七类设施：便利生活、娱乐休闲、商超购物、学习教育、医疗养老、公共空间、交通出行——定义与达标口径见 1.4；
- 综合分公式：`0.40×覆盖7 + 0.20×锚点三项（便利生活/医疗养老/学习教育） + 0.15×(1 − 锚点最近均值/X) + 0.15×交通分量（地铁 1.0 / 仅公交 0.6 / 缺失 0） + 0.10×min(1, 等时圈面积/直线圆面积)`，分母恒为当前 X；
- 白名单六城（北京/上海/杭州/成都/广州/深圳）完整体验；名单外照算，顶栏标「未做设施词表校准，仅验证方法」；境外坐标拒绝。

### 1.4 七类生活设施定义

| 类别 | 检索词（`$` = 或） | 达标口径 | 备注 |
|---|---|---|---|
| 便利生活 | 便利店 / 菜市场 / 农贸市场 / 理发店 / 快餐 / 蛋糕房 / 洗衣店 | ≥ 3 个且最近 ≤ X 分钟 | 综合分锚点三类之一 |
| 娱乐休闲 | 电影院 / 剧院 / 体育馆 / 游泳馆 / 展览馆 / 健身 / 洗浴 / 按摩 / 温泉 / 度假村 | 最近 ≤ X 分钟 | 商业健身计入本类，不计入公共空间 |
| 商超购物 | 购物中心 / 商场 / 超市 / 奥特莱斯 / 家居 | 最近 ≤ X 分钟 | 大型商超天然稀疏，覆盖权重已按此校准 |
| 学习教育 | 小学 / 中学 / 大学 与 幼儿园（双检索、幼儿园分体配额，防止单查询合并时挤占配额） | 最近 ≤ X 分钟 | 综合分锚点三类之一；重点学校带「重点学校」徽标 |
| 医疗养老 | 医院 / 社区卫生服务中心 / 诊所 / 药店 / 养老 / 敬老院 / 老年公寓 | 最近 ≤ X 分钟 | 综合分锚点三类之一；三甲医院带「三甲」徽标 |
| 公共空间 | 公园 / 图书馆 / 公共绿地 / 广场 | 最近 ≤ X 分钟 | 按名称核心度分级保留（公园/花园/绿地/景区/广场优先）；剔除政务网点、商业广场（写字楼分栋/卖场/停车场）与商业健身；体育场馆归娱乐休闲；<400 m² 的绿地面（环岛/绿化带误标）不计入 |

通用规则：每类最多保留最近 20 个 POI；步行分钟优先取自与等时圈同源的图引擎耗时（POI 吸附路网节点），吸不上时按「直线距离 / 70 m/min」估算并标 `estimated`；第三拍 RouteMatrix 实测校准自动跳过「边缘到达」点（面状设施标签在内部，实测走到内部点位口径天然偏大）。

启动与部署见「六、部署方法」。

## 二、设计思想

### 1. 两个场景回答两个问题

- 「我打算在这一带活动/居住，**附近有哪些小区**，离我多远」——场景 A 用轻量列表直接回答；
- 「**这个小区的生活圈到底怎么样**」——场景 B 用同一套引擎出等时圈 + 体检报告 + 综合分。

两个场景共用同一份小区基础数据（名称、坐标、售卖均价、租金区间、简介、照片）与同一个地理计算引擎，口径完全一致。

### 2. 等时圈沿真实路网生长，不是扣一个圆

「步行 15 分钟能到哪」的真实答案受三重约束：住宅楼穿不过、未架桥的河过不去、无步道快速路上不去。本项目把这三种约束显式建模成图论问题：

- **底图六层**：可步行路网（roads）、建筑面（buildings）、住宅面（residential，小区匹配）、水域（water）、绿地（green，面设施「边缘到达」）、硬阻隔（barriers，快速路/铁路/封闭汽车道），全部来自真实 OpenStreetMap 裁片；
- **建图规则**：与墙厚区或水域相交的边直接删除（天桥、人行地道除外）；阻隔线两侧的边不得跨越；建筑不是障碍而是「可进入性」问题（见下一条）；
- **建筑可进入性四类判定**：商场可穿行（1.1× 步速走大厅/底商廊道）、办公只走底商 8 m 廊道、住宅不可穿（外扩 1.5 m 墙厚）、开放场地按内部路网走。

在这个图上跑一次**截止 Dijkstra**（截止时间 = X×60 秒），一次搜索同时出 5/10/15 全部分层——等时斑天然贴路、让位建筑与水面。

### 3. 主圈只依赖本地底图，不等百度

等时圈测时**只用图上边权**；百度能力（POI 检索、RouteMatrix 实测耗时校准、步行折线对照）走**第三拍异步**，不阻塞出圈。快/精两拍先行：快拍约 300 ms 铺出沿路等时斑，精拍叠加建筑让位与设施检索。缓存命中毫秒级返回。

### 4. 地图渲染：百度只出瓦片，矢量全部自绘

百度地图只承担底图瓦片与手势；等时分层、路网、建筑四色、水域、阻隔、设施点全部由一张覆盖在地图容器上的自绘 `<canvas>` 绘制。路径按经纬度构建一次缓存为 `Path2D`，平移缩放只改变换矩阵。几千个矢量要素若走「一要素一 overlay」会撞上 BMapGL WebGL 管线的 framebuffer 崩溃，自绘方案 overlay 数为 0。未配 JS AK 或加载失败时自动降级为内置 SVG 底图，功能不受影响。

### 5. 报告可解释

雷达分、达标明细、体检诊断全部由同一份「最近步行分钟」数据推导，口径一致、逐条对得上；诊断句直接指认「哪一侧被什么挡住」，而非只报一个面积比。

### 6. 服务盲区灰块：1 km 内缺「菜市场/超市、药店/医院、小学」逐格判缺

赛题把「1 公里内是否缺菜市场/药店/小学」列为硬指标。本项目把它落成地图上可指认的**灰色盲区块**，而不是只给一个占比数字：

- **三组设施，按名称收窄匹配**：缺菜市场/超市（名称含 菜场/菜市场/农贸市场/生鲜/超市 的便利与商超类 POI）、缺药店/医院（名称含 药店/药房/医院/诊所/社区卫生服务 的医疗类 POI）、缺小学（名称含「小学」的教育类 POI）。便利店、养老院、幼儿园、中学等**不参与判缺**——幼儿园/中学凑不到小学的数，防「2.9 分钟就到学校却被计为全盲区」的假象；
- **网格判定**：中心所在等时圈面上铺 100 m 网格，每个格心独立判「自身直线 1 km 内有无该组设施」，无则该格计入缺失。判定半径**写死 1 km、不随 X 缩放**（赛题口径是固定的 1 公里）；判定域限定在等时圈内，圈外区域不判；
- **4-连通聚合成面**：逐类独立把缺失格聚合成连续区块，长宽比 > 3 的带状区域标记为「灰色走廊」（虚线描边）——沿河/沿铁路的狭长无设施带一眼可辨；
- **纹理区分、色盲友好**：三组缺失统一红色描边（不引入过多颜色），用纹理区分类别——斜线 ↗ = 缺菜市场/超市、斜线 ↘ = 缺药店/医院、圆点 = 缺小学，纹理间距按屏幕像素恒定，缩放不变形，黑白打印同样可辨；
- **图层默认开**：左下「图层」面板「服务盲区(1km)」默认开启，附同款纹理图例；双底图（百度 GL / 内置 SVG）纹理视觉一致。

## 三、创新点

1. **OSM 建筑外沿全量引入**：建筑不是简单障碍，而是按「可进入性」四类判定（商场可穿行 / 办公走底商廊道 / 住宅封闭外扩 1.5 m 墙厚 / 开放场地按内部路网），等时圈绕行行为与真实步行体验对齐；
2. **路网/水域隔断之后的连通恢复**：`bridge=yes` 天桥与 `tunnel=yes` 人行地道（footway/path/steps）允许跨越水域与阻隔，车行隧道不进步行图；高架道路类 barrier 行人在交叉口处以高架/地道形式穿越、不阻隔；河流、铁路、快速路等长线要素切片时按片 bbox 裁剪几何，避免整条河被复制进沿途每张片导致串片；
3. **设施点「边缘到达」判定步行时间**：面状设施（公园等）的 POI 标签常在设施内部，普通 30 m 吸附够不到路网——在 250 m 接驳半径内取「节点耗时 + 末段直线接驳」最小值，近似「到达设施边缘即算到达」；公园/绿地类面设施标签贴边 ≤60 m 时直接以「到达面边界」为准；这类点打 `edgeArrival` 标记，第三拍 RouteMatrix 实测校准自动跳过（百度实测走到内部点位，口径天然偏大）；
4. **设施在地图上一键定位**：达标明细悬停浮层内点设施名，地图 `panTo` 并挂高亮标记与名称标签（百度模式 3D 倒圆锥 / SVG 模式标签，双底图实现同款交互）；附近页列表「在地图定位」同款效果；
5. **重点设施打标加亮**：对 education/health/transport 三类按词表打标 `key_school`（重点学校）/ `sanjia`（三甲医院）/ `metro`（地铁站），在达标明细与悬停浮层中以徽标突出显示；
6. **一次搜索出全部分层**：截止 Dijkstra 一次搜索同时输出 5/10/15 全部分层，快拍约 300 ms；
7. **降级是显式契约**：六环外不硬算，走廊近似 + 「已降级」徽标，不把近似结果伪装成高精度；
8. **小区维度数据联动**：内置小区库（均价/租金/照片/简介）与路网评估打通——点哪评哪，资讯框即看小区基本信息，附近页与评估页互相跳转且状态保留。

## 四、系统技术架构

### 1. 分层结构

```
apps/web    Next.js 15 + TS + Tailwind + shadcn/ui + ECharts
  app/page.tsx          场景选择引导页
  app/nearby/           场景 A：附近小区生活圈
  app/evaluate/         场景 B：评估小区生活圈
  components/map/       MapView（百度 GL / 内置 SVG 双底图实现）、
                        自绘 canvas 矢量层、小区资讯框
  components/report/    ReportPanel（得分/雷达/明细悬停/诊断/打印）
apps/api    FastAPI BFF：编排、两拍出圈、缓存、百度代理、降级、
            SQLite 小区库查询（community/locate、community/nearby）
packages/geo 地理计算引擎包：底图加载/可进入性/建图/等时圈/打分/盲区/扇区
data        map_fabric 预切六层底图 + SQLite 小区库 + 演示快照
```

### 2. 北京六环内：真实 OSM 全量网格片（高精度）

六环内（覆盖面积约 3200 km²）全部使用真实 OSM 路网与建筑，按 4 km 网格预切，离线数据管线：

```
data/beijing-260927.osm.pbf（Geofabrik 北京抽取）
  → scripts/import_osm_fabric.py --ring6     # PBF → 六环全量六层 GeoJSON
  → scripts/tile_fabric.py --source ...      # 全量 → 4km 网格片（bbox 外扩 2200m 邻域）
  → data/map_fabric/b6r_rXXcYY/              # 每片 roads/buildings/residential/water/green/barriers 六层 GeoJSON
```

关键细节：

- **长线要素按片裁剪**：见「创新点 2」；water/barriers 两层按片 bbox 裁剪几何后再落盘；
- **按片名直取，不按点猜**：建图与底图接口均先算请求点所属网格片名（`tile_indices`），再对指定片裁切（`clip_region`），杜绝相邻片边界框重叠导致的错选；
- **TileManager 懒加载 + LRU 常驻 8 片**：首次点入新片现场建图约 2–5 s，命中缓存 <300 ms；
- **覆盖已验证**：ring6 边界多边形内均匀采样 11,167 点，逐点核对网格片，缺片 0 个；
- 四个样例区域（劲松/中关村/南苑/上地）另备**全量精修裁片**，启动即预热入内存，体验毫秒级。

### 3. 六环外与名单外区域：走廊近似（自动降级）

1. **动态走廊生成**：以请求中心为原点，向 8 个方向各取一条百度 DirectionLite **真实步行路线**，按 80 m/min 沿折线在各时间层截止处截断，缓冲 50 m 并取中心 100 m 缓冲的并集，作为可达区域近似；
2. **POI 与耗时仍走百度实测**：设施检索与 RouteMatrix 算路与六环内同一套第三拍逻辑，缺口结论依然真实；
3. **明确标注**：报告附「已降级」徽标，吸附说明注明「走廊近似」。

### 4. 引擎关键实现

- **图版本契约（graph_version，当前 v2）**：注入百度对照折线会新增节点/边，建图规则演进也会改变图结构——两者均以整数版本号显式声明；v2 起高速/快速路类阻隔不再整体切断步行图（行人在交叉口以高架/地道形式穿越）。节点级缓存键内嵌图版本，图一升级旧缓存整体失效，杜绝「旧 costs 配新图」的越界与脏数据；
- **两级缓存**：进程内，截止 Dijkstra 的节点耗时（`node_costs`）与整份精拍结果（`node_results`）按 `(region, node_id, minutes, graph_version[, blindFilter])` 键缓存，同中心同分钟重复请求毫秒级返回；磁盘上，整响应 JSON 按「中心坐标（约 1 m 精度）+ minutes + engine」落盘，TTL 24 h，跨进程复用；
- **启动期障碍预融合**：住宅墙厚区与水域在 RegionBundle 构建期一次性 `unary_union` 成单张障碍面，快/精拍直接 `difference`——真实 OSM 建筑动辄数千个墙厚区，逐请求求并是主要耗时，预融合后请求期零并集开销；
- **百度能力幂等注入**：第三拍对照折线以 `region|route|geohash5` 为键登记在 `baidu_injected`，重复触发不二次注入；未配 AK 或百度超时只影响对照层与设施检索，前两拍等时圈结果不受影响；
- **面属性回传复用**：绿地/水域面连同 OSM 属性（name/leisure 等）进入 RegionBundle，同时服务 POI 面感知「边缘到达」判定与公共设施名称回填（百度 place 对部分公园只有子设施 POI、无本体条目）；
- **城市白名单**：六城（北京/上海/杭州/成都/广州/深圳）以内置 bbox 判定、零外部请求；境外坐标直接拒绝；名单外区域照算但顶栏标注「未做设施词表校准，仅验证方法」；
- **SQLite 小区库**：`communities` 表 17 列（名称/归一化名/坐标/区县/商圈/售卖均价/一二三居租金区间/简介/综合分/打分时间），建 `name_norm` 与 `(lng, lat)` 双索引；定位接口两级命中（residential 面名精确匹配 → 500 m 坐标兜底），附近列表 haversine 全表扫描按距离升序。

## 五、核心算法设计

### 1. API 调用策略：批量并发、限流容错与空间插值

所有百度服务端调用（地理编码/逆编码/坐标转换/地点检索/RouteMatrix/DirectionLite）收敛到单一客户端，按同一条管线执行：

```
请求 → 两级缓存（进程内 dict + 磁盘 JSON，SHA1 参数键，TTL 24 h，.tmp 原子写）
     → 令牌桶限流（2 QPS，asyncio.Lock 内预支令牌排队，可注入时钟离线测试）
     → HTTP 请求（8 s 超时）
     → 失败重试（≤3 次，0.5/1/2 s 指数退避）
```

- **批量距离矩阵**：RouteMatrix v2 按单请求 50 对、10 起点自动切批；步行分钟校准每类只取直线最近 20 个 POI（七类合计 ≤140 终点，自动切 ≤4 批），实测分钟**只替换图上分钟**而非全量重算；
- **并发编排**：9 路地点检索一次 `asyncio.gather` 发出（五类常规词 + 教育/交通双检索），由令牌桶排队打满配额不超限；六环外走廊 8 方向 DirectionLite 并发且逐向容错，个别方向失败不影响其余；
- **配额预算**：快拍 0 次外部调用；精拍 ≤9 次检索 + ≤4 批矩阵 + ≤2 次路线。**主圈零矩阵原则**：等时圈与设施步行分钟都查同一次截止 Dijkstra 的耗时数组，RouteMatrix 只在第三拍做校准，且自动跳过「边缘到达」条目（实测走到面设施内部点位，口径天然偏大）；
- **容错与降级**——每一层失败都有明确出路，降级结果不落缓存防止污染：

| 故障 | 兜底 |
|---|---|
| POI 检索异常/超限 | 确定性合成 POI（geohash 种子，可复现），标注 `poi_ok=false`，结果**不写缓存** |
| 公园本体缺失（百度只有子设施 POI） | OSM 绿地面回填公共空间（≥400 m²、名称命中核心词，与已召回条目去重） |
| RouteMatrix 校准失败 | 保留图上引擎分钟，出圈不受影响 |
| 对照折线失败 | 静默跳过该层 |
| 官方等时圈接口无权限 | 捕获后仅追加一条诊断，以自建引擎为准 |
| LLM 诊断超时/格式不符 | 回退模板诊断，主流程不依赖 LLM |
| 六环外/无底图区域 | 8 方向走廊近似 + 「已降级」徽标（见「系统技术架构 · 3」） |
| 演示模式 | 预计算快照（150 m 命中）→ 确定性合成，共用同一套引擎 |

**创新的空间插值——扇形采样与走廊推导**（底图覆盖之外，不获取路网数据也能推导近似连通区域）：

- **8 方向扇形采样**：向 8 个方位各取一条 DirectionLite 真实步行路线（终点落在 80 m/min 直线圆边界上），折线天然沿真实路网、自动绕开水域与快速路——用极少数请求换回方向的连通性；
- **时间插值截断**：沿折线按 80 m/min 累计长度，越过时间层截止处时按**末段线性比例插值** `(cutoff − 已累计) / 末段长` 求出精确截断点，各时间层共用一条路线分别截断；
- **走廊融合**：各截断走廊缓冲 50 m，与中心 100 m 缓冲取并集成斑；成功方向 <3 时回退「最近区域底图」并显式标注降级；
- **8 方位达成率诊断**：等时斑与 8×45° 扇面对照圆求交得 `gapRatio`，最差方向生成「sector:NW …」方位徽标诊断（见「设计思想 5」）。

### 2. 等时步行圈生成算法

1. **内存建图**：六层 GeoJSON 载入后以 STRtree 空间索引求线线交点（含 T 型路口），交点按里程插入打断成图节点（毫米精度合并）；无分叉的连续同类路段做度 2 收缩，节点只留路口与端点（劲松裁片收缩后 1710 节点 / 2417 边）；
2. **边权 = 长度 / 步速**，步速按路面分级：路面 70、台阶 44、室内廊道 60 m/min、商场内 ×1.1。70 m/min 与百度步行算路实测（771 m/11.0 min、1815 m/25.8 min）对齐、天然偏保守；直线对照圆与直线估算口径用 80 m/min——两套口径保证「图上结果不虚标、对照基准不苛责」；
3. **三重约束建图过滤**：与住宅墙厚区（外扩 1.5 m）相交的段删除、与水域相交的段删除、跨越快速路/铁路阻隔线的段删除；`bridge/tunnel` 人行设施豁免可跨越；商场生成 ×1.1 内部廊道、底商建筑生成 8 m 外墙廊道环；
4. **起点吸附**：25 m 网格桶索引就近吸附（上限 30 m）；失败时全图最近节点兜底，并在报告注明「已吸附到最近可走点（约 X m）」；
5. **一次截止 Dijkstra**：堆实现、超截止剪枝，一次搜索返回全图节点最短耗时，5/10/15 各时间层从同一耗时数组按 `cost ≤ 层×60` 切片——**不逐层重跑**。one-to-all 场景下 A*/双向/收缩层级加速收益有限，普通 Dijkstra 对几千边的收缩图已是毫秒级；
6. **成斑（缓冲融合让位法）**：可达边各缓冲 30 m 后 `unary_union` 融合成斑，再 `difference` 启动期预融合的「墙厚+水域」单张障碍面；含起点的连通块为主圈，其余为飞地（过桥到达的对岸）计入总面积。不用凸包（虚报可达范围）、不用固定半径采样点连多边形（锯齿圆）；
7. **两拍共用一次搜索**：快拍取可达边凸包包络（**仍 difference 障碍**，快可以简化几何、绝不取消约束）约 300 ms 返回；精拍出建筑让位后的分层多边形。引擎自检断言进全量回归：快拍 <300 ms、精拍 <3 s、等时斑侵入通惠河面积 <0.01 m²。

### 3. 多源 POI 数据清洗与服务盲区识别

**POI 清洗链**（检索词直挂七类，`$` 为百度「或」语法）：

1. **双检索防挤占**：教育（小学/中学/大学 ‖ 幼儿园）与交通（地铁站 ‖ 公交站）各拆两次检索——合并单查会被幼儿园/公交站挤占单次 20 条返回配额，导致小学/地铁漏召回；
2. **噪声剔除**：公共空间两级黑名单（名称正则：政务网点、「购物/百货/SOHO/写字楼」类商业广场、写字楼分座「A座/东座」、卖场/停车场；百度一级类目正则：房地产/购物/公司企业/金融…）；交通剔除出入口/出站口/停车场与「××地铁站」通名后缀的冠名关联设施；
3. **去重与同名归并**：有 uid 按 uid 去重，无 uid 按「同名 + 直线 <30 m」合并；三类同名归并链——

| 设施 | 归并规则 | 例子 |
|---|---|---|
| 交通站 | 剥方向后缀（东/西/南/北/上/下行）→ 通名尾缀（地铁站/公交站/（地铁））→「地铁」品牌前缀 → 单「站」尾缀；(规范化名，地铁/公交) 相同只留最近 | 「地铁马连洼站（地铁）」=「马连洼（地铁）」=「马连洼站(北行)」 |
| 医疗机构 | 剥「-分支/科室」后缀；主机构名相同且相距 ≤200 m 视为同院区，只留最近 | 「××医院-急诊」并入「××医院」 |
| 公园多入口 | 去连字符/间隔号/空白后同名视为同一公园的多个门，只留最近；分区名不同保留 | 4 条「百旺公园」→ 1 条；「百旺公园三期」保留 |

4. **步行分钟口径**：图引擎分钟（250 m 边缘接驳内取「节点耗时 + 末段直线/70」最小值）‖ 面感知（公园/绿地标签贴边 ≤60 m 时按面边界 250 m 邻域耗时）两者取小；第三拍 RouteMatrix 实测校准替换；吸不上路网按「直线/70」估算并标 `estimated`；
5. **排序与截断**：每类 cap 20（截断前的圈内总数透出「20+」）；教育按幼儿园→小学→中学三段、交通地铁优先于公交、公共空间按核心词（公园/花园/绿地/景区/广场）优先——保证 cap 截断时「像公园的」不被写字楼挤掉。

**服务盲区识别算法**（业务口径见「设计思想 6」）：

```
域 = 主等时圈面；网格 100 m；判定半径 = 1000 m（固定，不随 X 缩放）
for 每个域内格心 c:
    for 组 ∈ {菜市场/超市, 药店/医院, 小学}:        # 名称收窄匹配
        若 c 直线 1 km 内无该组 POI → 该格该组计入缺失
逐组 4-连通聚合成缺失面 → 长宽比 > 3 的带状区块标「灰色走廊」
```

判定输入用**全量 POI（含圈外召回）**——圈外 900 m 的菜市场同样服务圈内格心，只拿圈内 POI 会系统性高估盲区；输出支持单类/复合筛选（`blindFilter`，缓存键同步隔离）。

### 4. 针对特定社区的真实对比方法

对比体系分三层，脚本化可复现（取数脚本 `scripts/compare_report.py`，劲松完整实例见下一小节；早期批次报告见 [docs/comparison-report.md](docs/comparison-report.md)）：

- **特定社区口径**：劲松/中关村/南苑/上地四个社区备全量精修裁片与样例中心（点击 150 m 内自动跑评估），上表结论可在演示模式（无 AK）下直接复现；

- **绕行系数全部落在 0.96–1.45（均值 1.22）**：图上耗时与直线估算同数量级、系统性偏大（绕行真实存在），无 >1.5 异常——底图路网拓扑无系统性偏差；<1 的个例（洁丰洗衣）是路网斜切反而更顺；
- **屏障注记可被独立核对**：最差方向稳定落在西侧（水域+东二环），东侧五向一致被东三环截断，20 分钟档南侧京津城际线开始起作用——扇区诊断识别的物理屏障与真实地理一致。5 分钟档综合分 43.5 偏低属预期：圈内医疗设施为 0（合成 POI 密度所致），该类计 0 分。

## 六、部署方法

### 1. 环境要求

Python 3.12+、Node.js 20+。Docker 可选。

### 2. 本地启动（四步）

```bash
# 1. 复制环境文件（无 AK 也能演示）
cp .env.example .env                          # Windows: copy .env.example .env
cp apps/web/.env.example apps/web/.env.local  # Windows: copy apps\web\.env.example apps\web\.env.local

# 2. 装依赖
cd apps/api && python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Windows
# .venv/bin/pip install -r requirements.txt     # macOS/Linux
.venv/Scripts/pip install -e ../../packages/geo # Windows
# .venv/bin/pip install -e ../../packages/geo   # macOS/Linux
cd ../web && npm install && cd ../..

# 3. 起 API（终端 1，端口 8000，cwd 必须在 apps/api）
cd apps/api && .venv/Scripts/uvicorn app.main:app --port 8000
# macOS/Linux: cd apps/api && .venv/bin/uvicorn app.main:app --port 8000

# 4. 起 Web（终端 2，端口 3000）
cd apps/web && npm run dev
```

**环境文件说明**：API 读仓库根 `.env`；Next.js 只读 `apps/web/.env.local`，把 `NEXT_PUBLIC_*` 写在根 `.env` 里不会生效。改完前端 env 必须重启 `npm run dev`（`NEXT_PUBLIC_*` 只在启动时注入）。端口被占用时 `npm run dev -- -p 3100` 换端口即可（API 的 CORS 已放行 localhost 任意端口）。

### 3. 配置百度 AK（可选）

在[百度地图开放平台](https://lbsyun.baidu.com/)创建两个 AK（服务端与浏览器端分离，均不进 Git）：

| AK | 填到哪个文件 | 需勾选能力 |
|---|---|---|
| 服务端 AK | 仓库根 `.env` → `BAIDU_SERVER_AK` | 地理编码、逆地理编码、地点检索、批量算路（RouteMatrix）、步行规划轻量（DirectionLite）、坐标转换 |
| JS API AK | `apps/web/.env.local` → `NEXT_PUBLIC_BAIDU_JS_AK` | JavaScript API GL（**浏览器端类型**）；Referer 白名单本地填 `localhost`（评审可临时填 `*`） |

两个 AK 相互独立：只填服务端 AK 出真实设施与耗时，底图仍是内置 SVG；只填 JS AK 有百度底图，设施走演示快照。服务端 AK 为空（或 `DEMO_MODE=true`）即为演示模式：共用同一套引擎，设施来自预计算快照 + 确定性合成，断网可演示，界面带「演示数据」徽标。切换模式改 `.env` 后重启 API 进程生效。

### 4. Docker Compose（可选）

```bash
docker compose up --build
# api → 8000，web → 3000
```

- AK 从根目录 `.env` 注入 api 容器，不进镜像；
- web 的 `NEXT_PUBLIC_*` 走 build args（`NEXT_PUBLIC_API_BASE`、`NEXT_PUBLIC_BAIDU_JS_AK`），改 AK 需重建 web 镜像。

### 5. 底图数据重建

见「系统技术架构 · 2」的管线命令；四个样例精修裁片由 `import_osm_fabric.py --bbox` 切出（劲松 `--bbox 116.436,39.868,116.480,39.901`，上地 `--bbox 116.290,40.024,116.334,40.068`，中关村/南苑见脚本内同名参数）。

## 七、其它与开源协议

### 测试与 CI

```bash
# 后端 + 引擎（全离线，不依赖 AK）
pytest apps/api/tests packages/geo/tests -q
# 代码风格
ruff check apps/api packages/geo scripts
# 前端
cd apps/web && npm run lint && npm run build
# E2E 冒烟（Playwright，不进 CI）
cd apps/web && npx playwright install chromium   # 首次
npx playwright test
```

- E2E 需先起好 API；Web 由 Playwright 自动拉起到 **3100** 端口（避开常见 3000 占用），`/api/*` 请求由测试代理转发到 8000；离线装不上浏览器时跳过即可，其余测试不受影响；
- GitHub Actions（`.github/workflows/ci.yml`）：`ruff` + `pytest`（Python 3.12）与 `npm run lint` + `npm run build`（Node 20）。
